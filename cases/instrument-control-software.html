CASE 03 · INDUSTRIAL PROTOTYPE

Reconstructing instrument behaviour into a software control system.

A control architecture for UV-Vis spectrophotometers where serial commands are not called directly from UI code. Protocol, hardware abstraction, instrument state, measurement algorithms and operator workflows are explicit layers with testable boundaries.

DomainUV-Vis control
ArchitectureLayered + stateful
VerificationReal hardware runs
BoundaryEmployer-associated
01 / Problem

A command protocol is not an instrument model.

Low-level commands expose capabilities but not the invariants that make measurements correct: sequential command execution, busy states, lamp/filter transitions, gain selection, beam configuration, wavelength movement and measurement-specific preparation.

The software therefore needs a canonical state model and workflow engine rather than a collection of button handlers around a serial port.

04 / Decisions

Control decisions must preserve measurement meaning.

Single command owner

A serialized command path prevents competing UI actions from corrupting physical instrument state.

State before rendering

The frontend observes canonical state and workflow outcomes rather than inferring success from visible controls.

Verification at boundaries

Lamp, filter and gain transitions are treated as engineering boundaries that can require delay, readback and additional evidence.

06 / What this proves

Scientific software architecture grounded in physical instrument behaviour.

This case demonstrates the ability to reconstruct an imperfectly documented physical system into explicit software contracts, preserve measurement semantics across layers and validate design assumptions against real hardware rather than frontend behaviour alone.
