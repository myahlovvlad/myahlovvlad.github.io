CASE 02 · INDUSTRIAL + PUBLIC TOOL

From static screens to executable instrument behaviour.

A workflow for formalizing instrument screens, physical controls, events, states and transitions before firmware handoff — then generalizing the method into a public HMI/FSM engineering workbench.

DomainEmbedded HMI
ModelFinite-state machine
OutputFirmware behaviour spec
Public proofLCD Bitmap IDE
01 / Problem

A screen specification is not a behaviour specification.

Static mockups describe appearance but leave critical questions implicit: which physical control causes an event, which states are reachable, what happens during a blocking operation, how the user returns from an error, and which transitions are valid.

The engineering task was to turn interface intent into a model that could be reviewed, simulated and transferred to firmware without relying on verbal interpretation.

02 / Behaviour model

Make every transition explicit.

03 / Decisions

The HMI is part of the instrument state machine.

Separate display from state

One screen can appear under different system conditions; behaviour should therefore be driven by explicit state, not by the fact that a bitmap is visible.

Bind physical controls semantically

Button presses become named events with guards and effects, making operator paths testable instead of visually implied.

Simulate before target integration

Runtime preview exposes dead ends, inconsistent navigation and missing transitions while they are still cheap to correct.

04 / Generalization

Industrial problem → reusable engineering tool.

The method became the conceptual basis for LCD Bitmap IDE: an offline environment for authoring embedded LCD interfaces, binding controls, modelling FSM navigation, previewing runtime behaviour and exporting firmware-ready assets.

05 / What this proves

Ability to formalize interface behaviour across design and firmware boundaries.

This case shows systems thinking rather than screen design: operator intent becomes explicit state, transitions become testable contracts, and the same formal model can drive review, simulation, automation and implementation.
